# 同作者去重、展示控制与 Feed 收录

> 历史阶段记录：用户后续决定先取消收录确认。人工申请/审核门槛由新增迁移 `0008_direct_feed_publication.sql` 和对应代码撤销；新作品直接进 Feed，更新保持原展示状态。同作者去重和作者隐藏/恢复继续生效，旧作品及名片不重写。下面保留当时的实现与验收，不代表当前仍需审核。

2026-11-16（America/New_York）已部署至 [独立测试站](https://funtrack-staging.zhayizha-pacificapie.workers.dev/site)。主站 Worker 版本 `28d56664-a51c-4849-94da-bcbe916688d4`。仅更新 `funtrack-staging`；原 Sites、production 数据库和云构建器部署不变。

## 用户流程与规则

- 新发布作品可以立即分享、试玩和制作名片，默认不进入 Feed。
- 我的作品 → 更多 → 申请进入 Feed：选择网页游戏、互动叙事或可玩原型，说明玩家操作与反馈，并确认已试玩、有权发布。
- 收录允许未完成的可玩原型，不要求分数或输赢；普通工具、静态作品集、广告页及重复发布不收录。作者须注明使用的原作与素材来源。
- 人工试玩后审核。上传成功和审核通过均不是原创认证，也没有自动判定“是不是游戏”的模型。
- 收录管理员在创作中心 → 管理 → 收录管理打开试玩，再通过或填写修改建议。审核接口同时校验权限、作品当前版本及收录 revision。
- 我的作品 → 更多 → 从 Feed 隐藏：退出 Feed、搜索、公开作者作品列表和相关推荐；原链接、既有名片、历史版本、统计继续保留。隐藏不是私密访问控制。
- 已批准的当前版本可以恢复到 Feed。新版本发布、回滚或名称/介绍/封面实际更改都会使已提交作品重新待审，隐藏状态保持不变。尚未申请的作品仍不自动申请。
- 已有六件作品保留当前展示，迁移备注为“历史作品保留展示”，不伪称曾经人工审核。旧作品后续修改后，需要补齐类型与玩法说明才能通过新一轮收录。

## 去重边界

同作者范围内，对 HTML 原始字节计算 SHA-256，跨上传方式、隐藏作品和所有历史版本检查。外链用规范化后的完整 URL 精确比较。存量重复作品保留，不合并、不删除。

| 情况 | 结果 |
| --- | --- |
| 同作者重新发布同文件或同链接 | `DUPLICATE_WORK`，打开已有作品或更新版本 |
| 更新为当前版本的同文件 | `VERSION_UNCHANGED`，引导编辑作品信息 |
| 更新为本作品已有历史文件 | `VERSION_ALREADY_EXISTS`，引导查看和切换历史版本 |
| 更新为该作者另一作品的已有文件 | `DUPLICATE_WORK`，指向另一作品 |
| 不同作者使用相同文件 | 独立处理，不泄露或合并他人的作品 |

幂等重试返回原操作结果；不同请求并发竞争由数据库唯一指纹与发布事务保护。拒绝的提交不增加作品或版本，并清理本次临时文件。滚动部署期间未写入新指纹的旧代码数据仍有历史版本查询兜底。

这是精确内容去重，不是抄袭检测：重新构建产生不同字节、修改文件注释、不同部署 URL 均可能不命中。共创、跨作者归属与相似内容识别留到后续。

## 数据与部署

迁移 `0007_work_publication_controls.sql` 新增 `ft_work_discovery`、`ft_work_fingerprints` 及收录状态触发器。原表原行不改写。先导出 staging D1 并用副本预演，再应用迁移，最后发布 Worker。全程没有删除旧作品或 R2 文件。

审核身份由服务端 `FUNTRACK_REVIEWER_IDS` 白名单配置（逗号分隔的可信用户 ID），不能由请求头或浏览器自报。staging 已配置当前真实 Clerk 作者账号；其他账号没有审核入口/权限。后续部署需重新核对目标环境的身份，不能跨 Clerk 实例复制用户 ID。

`GET /api/works?mine=1` 提供作者私有分页，不受 Feed 资格过滤；前端逐页读取自己的作品，隐藏作品依然可以选入名片。公共 `/api/discover` 即使 author 为本人，仍只返回公开收录作品。

注意：作品信息编辑的幂等 `work` 回包是操作快照，可能含编辑前的收录状态。现有界面成功后会重新 GET 最新作品；Feed 查询与审核 CAS 使用最新数据库状态。未来 API 客户端也应刷新作品，不将旧操作快照当作当前审核结论。
