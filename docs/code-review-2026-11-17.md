## 本轮已修复

1. **评论缺少版本上下文。** 追加可空 `version_id`，由服务端验证版本属于同一作品；版本名称来自不可变版本记录。新旧版本共用讨论区，回复保留自己所处页面版本。历史记录和旧客户端保持未知，不回填当前版本，也不将版本关联当作试玩证明。
2. **互动入口无法直达较旧评论。** 链接携带评论 ID；有界 context 读取目标及根评论，在独立定位区展示，不污染普通列表分页。不存在、跨作品响应和加载失败有对应处理。
3. **定位响应与普通列表响应的竞态。** 初版会在普通列表迟到时重建定位 DOM，丢失高亮/键盘焦点。复现后已修复，并让测试 DOM 按浏览器语义销毁旧节点，避免假测试掩盖问题。
4. **切换账号后旧评论草稿误写到新账号。** 真实鉴权客户端、评论 UI 和 SQLite router 串联复现了 A 页面取到 B 的合法会话后先写入、再因回执不匹配报错。新评论请求携带固定的 `expectedAuthorId`，服务端在任何回执读取或写入前校验；不匹配拒绝写入，保留草稿及提交标识。此字段不是身份来源。
5. **文档与实现的冲突。** API 总述更新为独立 Clerk 鉴权边界，去掉“没有贡献加权”的过期描述；数据文档明确新评论版本上下文不自动改变原有统计口径。迁移说明改为审阅手写追加 SQL，并说明生成器快照滞后。

## 未修发现与优先级

### P2：评论限流的检查与写入不是原子操作

位置：`lib/funtrack/server.ts` 的 `rateLimit()` 与 `addComment()`。多个请求可以同时读到尚未达到 30 条的结果，再分别成功写入。

证据：在真实 router 和 SQLite fixture 上，让 40 个额度查询读完后同时释放，40 个请求全部返回 201，实际保存 40 条；普通不协调并发时为 30 成功/10 拒绝。协调响应只固定一个可发生的执行顺序，没有修改 SQL 或绕过认证。第二位审查者独立复现。

建议下一次将额度检查与插入放在同一原子条件写入或事务内，并保留已完成幂等请求的重放语义。曝光/推荐已有独立原子约束，不能把评论的这一缺口泛化为其去重失效。本轮未扩大为整站限流改造。

### P2：普通讨论列表请求缺少可恢复的截止时间

位置：`public/discussion.js` 的 `load()` 和 `public/site.js` 的通用 `api()`。初次普通列表请求一直 pending 时，`state.loading` 不会退出，`state.loaded` 仍为 false，发布按钮持续不可用。新 context 请求的 12 秒截止时间不覆盖普通列表。

这是代码路径审查发现，未声称在云端制造了故障。建议复用有界请求机制，为主列表及必要写操作提供截止时间、取消和显式重试，并测试迟到响应不会复活旧页面。

### P2：其他无所有者对象的新写操作尚未统一绑定页面账号

评论入口本轮已修复，但通用 `api()` 仍会读取调用时的合法会话；账号在另一标签页切换后，旧页面的新作品发布、点赞等意图还没有统一的页面账号检查。账号切换发生在 `getToken()` 调用期间的竞态已有保护，发生在调用之前则属于不同情况。

评论路径已通过串联测试复现并修复；其他入口为共享实现的代码审查结论，尚未逐项进行真实多账号云端验收。这不是 Clerk 认证绕过；已有作品编辑/版本操作另外受服务端所有权校验保护。建议下一轮在统一写入口引入预期账号检查，再逐条回归，不分别复制不同的检查规则。
