## 修复细节

### 原子限流

`lib/funtrack/server.ts` 的 `/api/sessions`、`/api/events`、`/api/feedback` 和 `/api/sessions/:id/events` 改为 `INSERT … SELECT … WHERE COUNT < limit`。反馈被拒绝时不会发放贡献积分。会话事件批次可能提交一个合法前缀后返回 429；客户端保留事件 ID，窗口恢复后重放已接收事件、补齐剩余事件，不重复记账。

新增 5 个行为测试，固定“多个旧检查同时读到剩余一个额度”的并发顺序。修复前 5/5 失败，修复后 5/5 通过；覆盖账号隔离、额度恢复、重复提交、内容冲突和独立事件/会话批次争夺最后额度。另将真实路由生成的 310 条写 SQL 放入全新本地 D1，验证最终会话 30、总事件 240、反馈 30，批次仅写入剩余的 1 个事件。

### 完整请求期限

新增 `public/api-request.js`，在 `site.js` 的统一 API 入口包住鉴权、fetch 和 JSON 读取。读取 15 秒，普通写入 30 秒，GitHub 导入/构建创建 60 秒，文件表单 90 秒，捕获请求最多 45 秒（媒体控制器已有的 40 秒取消仍可提前生效）。统一入口不自动重试写入；现有业务控制器的重试规则不变。

测试覆盖：token 永久等待、迟到的 token 不得发送写入、响应体等待、外部取消、已经取消的请求不发送，以及名片超时后按钮恢复并使用相同幂等键。这里的客户端超时不承诺服务器事务被撤销，必须保留幂等重试。

### 媒体额度与降级

`public/publish-media.js` 保留 `CAPTURE_LIMIT` / `BROWSER_UNAVAILABLE`，提供明确中英文说明。自动捕获失败后仍可选手动封面或明确跳过，继续发布。

现有发布前截图预算：100 秒/次、1,000 秒/日、27,000 秒/月，约 10 次/日、270 次/月；视频：90 秒/次、900 秒/日、9,000 秒/月，约 10 次/日、100 次/月。各作者和新旧捕获入口共享预算，旧入口的不同预留量也会占用池子；这些是当前预留量折算，**不是实际成功作品数或并发容量承诺**。失败和重拍也会消耗次数。扩大推广前需按预计发布量确定容量和预算，不能靠 UI 修复获得更多配额。

### 异常记录

新增 `lib/funtrack/error-reporting.mjs`。未知异常返回通用 500 和 `requestId`，对应日志仅包含白名单事件/操作/异常类别，不记录 token、Cookie、请求正文、URL、SQL、原始异常 message/stack/cause。预期 4xx 不记为异常。日志写入失败不覆盖原始响应。

这是最小的关联与分类能力，不等同于完整调用链、外部监控或告警。两个独立部署配置启用 observability、关闭 invocation logs；尚未部署生效。测试验证原始错误中的敏感值不会进入响应和日志。

2. **联合恢复演练**：先明确恢复时间点和可接受的数据损失/恢复时长；取得相匹配的 D1 备份与 R2 对象清单；恢复到隔离资源，核对版本/metadata/名片引用的对象存在性和哈希，检查 owner、发布回执和历史快照，并走一次登录后试玩/分享。记录实际耗时和缺失对象；演练不能覆盖正式资源。
3. **监控验收**：部署修复到 staging 后，注入一次受控内部异常，确认响应 requestId 能关联日志；再验证选定的 5xx、Cron/构建失败及媒体预算告警确实到达负责人。记录查询、触发时间、收到时间和处理人。不要为了演练引入公开的故障触发接口。
4. **真实使用验收**：至少一个全新账号、一个真实 iPhone/Safari 和微信打开分享；覆盖目标地区网络，保留设备、系统、网络和结果。桌面浏览器 320/390px 模拟不能替代此项。
