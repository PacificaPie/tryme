# Funtrack API contract

All endpoints require Sites-injected `oai-authenticated-user-id` and `oai-authenticated-user-email`; missing identity returns 401. No production mock identity is accepted. Local tests must explicitly supply these headers. Every POST also requires an exact same-origin `Origin` (never `null`) and `X-Funtrack-CSRF: 1`. Browser requests use same-origin credentials. Errors are JSON `{error:{code,message}}`, with 400/401/403/404/409/413/415/422/429/503 as appropriate. Responses are `Cache-Control: no-store` unless an immutable media response states otherwise.

`Work = {id,authorId,authorName,name,desc,source:'html'|'url',versionId,version,coverUrl,url?,build?,createdAt,revision,updatedAt}`. GET work list/detail additionally include live `likesCount:number, likedByMe:boolean, commentsCount:number`. Comment totals include roots and replies from the new discussion table only. These live fields are not frozen in `Card.works` snapshots. IDs are opaque strings. `version` initially is `v1`. Missing cover is `coverUrl:''`. HTML launch is `/game/:versionId`, obtained when creating a session. Existing URL works never report inferred gameplay starts.

`Card = {id,authorId,name,bio,signature,headline,website,backStyle,template,workIds,works:Work[],createdAt}`. All details are flat fields supplied by the author: `signature` ≤80 characters, `headline` ≤120, `website` empty or an HTTP(S) URL without credentials ≤2000, `backStyle` one of `ink|ivory|cobalt`. Omitted details default to empty strings and `ink`. Publishing appends an immutable snapshot and updates the current author's profile in the same transaction; generating/changing a client draft has no server effect. Only owned works may be included. Old snapshot JSON is never rewritten or populated from a newer profile; read responses supply only empty/ink compatibility defaults. Existing default-detail idempotency keys remain replayable across the upgrade. No AI calls occur. New clients submit `workRefs` matching `workIds` in length/order, frozen from the preview. Each version must belong to that owned work; a later publication does not replace that reference. Legacy clients omitting `workRefs` retain save-time-current behavior. Neither form changes already saved snapshots.

Work likes store at most one row per authenticated user and work. Repeating `liked:true` cannot add a second like; repeating `liked:false` cannot decrement another user's like. No actor ID is accepted from the body. The returned count is the current stored total, not a client increment; it is separate from feedback of type `喜欢`. Clients serialize changes for the same work and use the acknowledged response (or re-fetch after an uncertain request), rather than issuing old and new intent concurrently. Concurrent distinct commands resolve in database execution order. Card snapshots use the standalone GET like endpoint for current social state; the snapshot itself stays immutable. This release does not add card likes, payments, or billing.

Discover sorts the entire filtered dataset before applying the page limit. Newest uses `createdAt DESC, id DESC`; popularity adds the stored like/comment count as the first descending key, with the same deterministic date/ID tie-break. Comment ranking includes roots and replies. `q` is a literal substring (`%` and `_` are not wildcards); SQLite's built-in lowercasing makes ASCII letter matching case-insensitive, and Chinese text matches by substring. Changing q/source/sort/author requires clearing the cursor. The cursor contains the first request's `asOf`, filters and last sorting tuple; page size may change within 1–48. `total` counts all matching works created by `asOf`, not the number already loaded. `nextCursor:null` means there is no following page at that read.

Discover ranking excludes works, comments and likes created after `asOf`; the returned Work social counts and viewer's `likedByMe` are live so they do not reverse a recently acknowledged interaction. Refresh starts a new ranking traversal. This is not a transactionally frozen feed: cancelling a like deletes its row, so a later page cannot reconstruct that like's former count and can repeat or omit an item under concurrent unlike activity. Clients deduplicate appended works by ID. No strict high-concurrency snapshot guarantee is claimed. The existing `/api/works` endpoint retains its original 200-row behavior for compatibility; new Feed/author browsing should use discover, and creator work pickers should page discover with `author=user.id` rather than discard older selections.

`Comment = {id,workId,workName,authorId,authorName,isCreator,body,parentId,createdAt,likesCount,likedByMe,replyCount}`. `isCreator` is derived from authenticated author identity versus the work's author; request-body identity fields are never trusted. Root comments have `parentId:null`; a reply may target only a root on the same work. Replies to a reply, cross-work parents and missing parents fail. A root's `replyCount` is the real total; replies have zero children. Bodies are plain text, not trusted HTML. Comment create rate limit is 30 new records per authenticated account per minute; replaying a completed key does not consume another record.

`RootComment` additionally includes `replies` (the first three replies, oldest first) and `repliesNextCursor`. Pass that cursor to the root's replies endpoint to continue after the embedded replies. Root pagination uses creation order newest-to-oldest; reply pagination uses oldest-to-newest. Internal monotonic database sequences handle same-millisecond creation consistently. Treat cursors as opaque, URL-encode them, and keep them bound to their original work/root/inbox. `nextCursor:null` means there are no more rows at the time of that request. The creator inbox is flat and includes the creator's own replies, distinguished by `isCreator`. Comment likes use the same per-user set semantics as work likes, without exposing liker identities.

Comments are visible to authorized viewers of the work within the Site's existing access policy. They are stored only in `ft_comments`/`ft_comment_likes`. No historical `ft_feedback` rows are migrated, copied into discussions, returned by comment APIs, or counted as comments. Legacy feedback endpoints and their owner-only visibility remain unchanged. The Site remains private. The new `collection` (点亮收藏) card template is accepted alongside unchanged `fold` and legacy `wall` snapshots.

Write receipts and session `accepted` items additionally include `clientEventId`, matching the input event ID for client queue acknowledgement. Their `id` is the durable server record ID; `duplicates` contains the client event IDs. Clients must clear pending events using `clientEventId`, not the server ID.

Uploads: self-contained `.html`/`.htm`, MIME `text/html`, UTF-8, at most 8 MiB (8,388,608 bytes); cover PNG/JPEG/WebP, at most 2 MiB, matching MIME and magic bytes. R2 writes must finish before a work/version is committed. An unsuccessful upload is never listed as published. HTML external dependencies are blocked by the game CSP. POST multipart body limit is 10,616,832 bytes: 8 MiB HTML + 2 MiB cover + 128 KiB for boundaries, headers and ordinary text fields. HTML limits use UTF-8 byte length, not string character count. Initial publication and version updates share these limits through `lib/funtrack/limits.mjs`.

GitHub import uses anonymous requests to fixed GitHub API/raw hosts, resolves the requested branch/tag to a full commit SHA and returns a pinned source permalink. It does not clone repositories, run build tools, use private-repository credentials, or fetch arbitrary dependency URLs. Common external/runtime dependencies are rejected as unsupported; these checks are conservative compatibility checks, not proof that every JavaScript path is self-contained. The existing uploaded-game sandbox/CSP remains the security boundary. Redirects, ambiguous slash-containing branch links, invalid UTF-8, oversized responses and non-HTML files fail explicitly. Each direct-HTML upstream request has a 10-second timeout and an 8 MiB response limit, checked against both Content-Length and actual streamed bytes; decoded HTML is validated again by the same upload validator. Repository-identity metadata/feed requests retain their separate 1 MiB cap. Anonymous GitHub quotas are shared by originating IP; rate-limit errors return 429 and the user may upload the file instead. The UI converts the returned HTML into a File and uses the normal review/upload flow; importing alone never publishes. Users must have rights to redistribute the selected content; a public repository is not by itself permission to rehost it. Returned provenance is shown for review, not persisted as a new Work field in this release.

Session events: types are only `play_start`, `game_complete`, `session_end`; max 20 events per batch. IDs are 8–128 URL-safe characters, seq is an integer 1–10000, elapsedMs is 0–3,600,000. Session expires after 60 minutes and belongs to the requesting user and exact work version. Duplicate event IDs, sequence numbers, and repeated start/end/completion are not counted again. Start must precede completion. An unplayed session may end without a start; ending never implies a start. `result` may contain a finite numeric `score` and `label` ≤120 characters. Server `receivedAt` is authoritative for receipt time. Accepted client events are self-reported, never verified engagement or verified human counts.

The game response enforces `CSP: sandbox allow-scripts; default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data: blob:; font-src data: blob:; media-src data: blob:; connect-src 'none'; child-src 'none'; form-action 'none'; base-uri 'none'; frame-ancestors 'self'`, plus HTML content type, nosniff, no-store and no-referrer. SDK reads random `bridge` from URL hash and sends `{channel:'funtrack-game',version:1,bridge,type:'ready'|'input'|'complete',result?}` to the exact server-injected parent origin. First trusted input is reported without keys or coordinates. `window.funtrack.complete({score,label})` reports one completion. Parent validates exact iframe window, opaque origin `null` and bridge. Ingest token, user identity and authentication data never enter the child HTML or its URL.

Analytics use server receipt timestamps and UTC date buckets. `scope:"work_period"` means all versions of the work in `[from,to]`; `byWork.currentVersionId` is only the present pointer, never the version attribution of aggregate counts. No version filter is introduced. Receipts carry actual version IDs. `views` means stored work-view events; `starts` means sessions with an accepted play_start; `ends` means session_end. URL works return `starts:null, ends:null` in byWork. `feedback` counts only legacy private feedback records; `comments` separately counts new discussion roots plus replies. Both summary and per-work counts use the same selected days window, owner scope and work filter. Work list/detail `commentsCount` is the all-time discussion total. Empty datasets return zeros/empty receipts, not seeded numbers. Latest receipt list is bounded to 30. Optional versionId on page events and feedback must belong to the stated work; omission on first acceptance selects its current version; an accepted event/feedback key replays its stored version even if current has since changed. Explicitly changing a retry to another version returns409. Clients freeze versionId when queueing, not when retrying. Private Site access is unchanged.


## Work versions and publication operations

`Version = {id,workId,version,ordinal,releaseNotes,contentHash,createdBy,createdAt,coverUrl,source,build?}`. `version` is the immutable `vN` label, `ordinal` its integer sequence. Existing artifact hashes are explicitly null until independently computed; new initial publications and updates store SHA-256. Build provenance is frozen per version, including repository, pinned commit and artifact hash; local-file versions do not inherit another version's build provenance.

`Operation = {id,action:'publish'|'activate',fromVersionId,toVersionId,previousRevision,revision,changed,createdAt}`. Works start at revision1. Actual pointer changes increment revision monotonically; a rollback does not decrement it, renumber history or copy files. New publication after v2→v1 is v3. Activating the current version is a recorded no-op with unchanged revision and updatedAt. Every activation, including a no-op, requires matching expectedRevision. createdAt remains the original work publication time and discovery ordering does not change.

Update/activate are HTML-only; names, descriptions, source and URL editing are outside this phase. Omitted cover inherits the current version's immutable resource key; a rollback restores the target version's own cover. File validation is shared with initial publication (8 MiB HTML/2 MiB cover); ready buildId fetches a hash-checked artifact up to 8 MiB without sending it inside the multipart request. Invalid, incomplete or another owner's build fails before any pointer change. Draft preview is sandboxed and does not create gameplay events.

Operation idempotency is unique per owner/key across works and operation types. The request hash includes action, work, expected revision, fixed game hash/build ID, cover replacement or inheritance, and release notes. Completed-key lookup takes precedence over current revision checks. Replaying an old successful publish/activate returns its original immutable version/operation and never executes the pointer update again; current state is separate. Same key with different content returns409 IDEMPOTENCY_CONFLICT. Initial POST /api/works preserves historical keys and returns its original v1, even after later updates.

A stale revision returns409 `{error:{code:"VERSION_CONFLICT",message,current:{versionId,revision}}}` only to the owner. Clients keep the draft and require an explicit refresh/rebase before changing expectedRevision or replacing the request key. This prevents v1→v2→v1 (ABA) from accepting a request based on the first v1. Cross-work target versions return404 VERSION_NOT_FOUND. Non-owners return403 NOT_OWNER.

New resource keys are written before one D1 transaction inserts the immutable version/operation and conditionally switches the pointer. The final SQL NOT NULL guard forces rollback if any inserted operation failed its pointer/revision invariant; a zero-row CAS is not treated as a transaction failure merely by throwing in JavaScript. CAS mismatch inserts no version/operation. Concurrent identical keys replay one operation; competing different content cannot both win. On uncertain commit responses the operation is read before orphan cleanup. Failed recovery reads retain possibly committed objects. Normal rollback never removes resources.

Existing sessions and event/feedback records retain their original version, including sessions completed after an update. Old game/media URLs remain readable under the existing Site access policy and sandbox CSP. Likes and public comments remain attached to workId. Saved card snapshots and explicitly previewed version references stay pinned. This phase adds no version deletion, artifact garbage collection, source conversion, automatic GitHub release or live reload of existing games.

Session-end events may include `result:{timingVersion:1,activeMs}`: integer visible-play milliseconds between 0 and 3,600,000 and no greater than elapsedMs. Legacy end results remain null. Missing old timing is never backfilled. See [analytics definitions](analytics-contract.md).


## Import capabilities and failures

`GET /api/builds/capabilities` and the existing `/api/builds/availability` return the same additive shape, under normal Sites authentication and `Cache-Control: no-store`:

```json
{
  "online": false,
  "configured": true,
  "status": "offline",
  "heartbeatTtlSeconds": 90,
  "lastHeartbeatAt": null,
  "limits": {"htmlBytes":8388608,"coverBytes":2097152,"publicationBytes":10616832},
  "imports": {"html":true,"repository":false},
  "repositoryRequirements": ["public","vite","npm-lockfile","root-license"]
}
```

`configured` means a sufficiently long runner secret is configured, not that a worker can build. `online` additionally requires a stored heartbeat newer than 90 seconds. `status` is `unconfigured`, `offline`, or `online`. A response is a point-in-time observation; creation checks availability again and may still reject if the heartbeat expires. These GET routes only read the latest heartbeat and never expire, claim, cancel or alter jobs. They expose no runner token, worker ID, lease or owner job data. `imports.html` is independent of the runner; it does not promise GitHub network availability or that an arbitrary HTML file is self-contained.

Repository builds still require a public repository with a root Vite npm project, build script, package-lock v2/v3, registry dependencies and root LICENSE. The current builder does not execute arbitrary `build.mjs`-only projects or provide backend hosting. Users may build a self-contained HTML locally and upload it, or publish a deployed URL where a backend/runtime network is necessary.

`POST /api/builds` retains idempotent job creation; offline creation returns 503 `BUILD_RUNNER_OFFLINE`, missing configuration returns 503 `BUILD_RUNNER_UNCONFIGURED`. Existing completed-key retries retain their original behavior. Owner-only build JSON now includes `errorCode` alongside the existing human-readable `error` when a job fails. Runner `POST /api/build-worker/:id/fail` accepts optional `code`; known codes are allowlisted, unknown/legacy codes become `BUILD_FAILED`. The code is stored in existing job metadata, requiring no migration. Expired jobs report `BUILD_TIMEOUT` or `BUILD_QUEUE_TIMEOUT`. Logs/errors remain redacted. Existing worker Bearer authentication and 10-minute lease rules are unchanged.

| Category / stable codes | Meaning / next action |
| --- | --- |
| `BUILD_RUNNER_OFFLINE`, `BUILD_RUNNER_UNCONFIGURED` | Repository building is unavailable. Upload a locally bundled HTML, or retry when a worker is available; single-HTML GitHub import remains usable. |
| `GITHUB_PRIVATE_REPOSITORY` | Upstream metadata explicitly reports non-public access. Use content you may publish through a supported public source or local HTML. |
| `GITHUB_NOT_FOUND`, `GITHUB_INACCESSIBLE` | Content cannot be read anonymously (404; or 401/403 without rate-limit evidence). A 404 does not distinguish private from missing; check URL/access or upload authorized local HTML. |
| `GITHUB_MULTIFILE_PROJECT` | A direct HTML import references other files/runtime resources. Use the supported repository builder, locally bundle to one HTML, or publish a deployed URL. |
| `UNSUPPORTED_PROJECT`, `UNSUPPORTED_LOCKFILE`, `UNSUPPORTED_DEPENDENCY`, `LICENSE_REQUIRED`, `EXTERNAL_ASSET` | Builder compatibility/redistribution requirements were not met. Fix the specific requirement or supply a self-contained HTML; required network/backend behavior needs a deployed URL. |
| `HTML_TOO_LARGE`, `GITHUB_FILE_TOO_LARGE`, `BUILD_ARTIFACT_TOO_LARGE`, `OUTPUT_TOO_LARGE` | HTML/artifact exceeds the applicable limit; final hosted HTML is at most 8 MiB. Compress/remove embedded assets, or use a deployed URL. `OUTPUT_TOO_LARGE` can also indicate aggregate intermediate-output limits. |
| `BODY_TOO_LARGE`, `COVER_TOO_LARGE`, `ARCHIVE_TOO_LARGE` | Multipart envelope, cover, or repository archive exceeds its separate limit. Covers remain 2 MiB; the builder's compressed archive limit remains 16 MiB and unpacked contents 64 MiB. |
| `GITHUB_RATE_LIMITED`, `GITHUB_TIMEOUT`, `GITHUB_UNAVAILABLE` | Upstream availability issue, distinct from project compatibility. Retry later or use local HTML. |

The response's `error.message` remains useful detail; clients should classify by code rather than matching translated text. Capability endpoints and larger upload limits do not change the opaque-origin game sandbox, owner authorization, version CAS/idempotency, old version resources, or saved card references.
