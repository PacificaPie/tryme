# Feed 扩展与界面质感：实施参考

本轮只读检查 `public/site.js`、`site.css`、`surface.css`，并阅读以下一手资料。本文是设计建议，不代表已经实现或完成浏览器验收。数值为 Funtrack 的建议起点，不是参考产品的硬性标准。

## 五份直接可用的资料

| 官方资料 | 原文支持的具体做法 |
| --- | --- |
| [Linear：A calmer interface for a product in motion](https://linear.app/now/behind-the-latest-design-refresh) | 让主要任务内容获得注意力；统一操作位置；减少多余图标、边框与界面特殊情况；使用设计 token 统一调整基础界面。 |
| [web.dev：Typography](https://web.dev/learn/design/typography) | 同时考虑字号、行长、行距与用户缩放；使用相对单位和有上下限的缩放，避免仅用视口单位控制字体。 |
| [web.dev：Optimize Cumulative Layout Shift](https://web.dev/articles/optimize-cls) | 为图片、iframe 和异步内容预留空间；可以用 `aspect-ratio`、`min-height` 减少突然位移；不能凭代码观察声称 CLS 已达标。 |
| [Apple HIG：Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons.md) | 突出最可能的动作；提供按下及进行中状态；确保点击区域与间距足够。其 44×44 pt 是 Apple 平台建议，不能直接当作网页 CSS 像素标准。 |
| [Base UI：Dialog 的焦点管理](https://base-ui.com/react/components/dialog#custom-focus-management) | 明确打开与关闭后的焦点位置；触摸打开时避免无意唤起键盘。这里借鉴交互规则，无需把现有原生页面重写成 React。 |

## 最值得落地的五项变化

1. **收小最新作品区，让目录成为 Feed 主体。** 当前只要有三件作品，就生成完整深色大封面加介绍区；其他作品因此被推到下面。建议最新作品与其他作品处于同一浏览层级：桌面最多使用约 200–240px 的紧凑横条，手机改为普通作品卡或短横条。保留真实名称、作者和一句玩法即可，删除横条中与整卡入口重复的显著按钮。排序切换后无需重新安排整页视觉中心。这是根据 Linear 注意力分配原则作出的设计推断，不是复制其页面。

2. **固定目录节奏，同时让次要信息真正可读。** 当前 `.store-grid:has(.work-tile:nth-child(5))` 会让同一视口的四件结果用两列、五件结果用三列。移除按数量切列，改为只由视口控制列数；卡片标题最多两行、简介一行，作者与互动始终在同一底行。建议正文从 14–16px、作者/元信息从 12–13px 起调，使用 `rem` 与无单位行高；避免同时采用很小字号和很淡文字。数字只是本产品的起点，不能当成 web.dev 的强制值。验收：4→5 件搜索结果卡宽不跳变，长中文标题、长英文名及 200% 缩放不遮挡操作。

3. **把质感收敛到少量语义 token，减少覆盖层。** 先统一正文/次要文字、页面宽度、三档间距、两档圆角与控件高度；同一类按钮、列表标题、输入框只保留一个最终规则来源。整合 `site.css` 与 `surface.css` 中本轮触及的重复声明，避免再追加第四层补丁样式。作品与名片素材负责个性，外层导航和表单保持一致。这是从 Linear 的一致性做法推导出的本地工程方案，不需要重做全站设计系统。

4. **让开局、退出和回执出现时页面保持稳定。** 当前详情封面按 1.6 比例，游戏 iframe 则为固定高度，再加工具栏与结果区；窄屏开局前后高度差较大。为游戏媒体区定义一致的响应式容器规则，封面、加载态和游戏共用同一空间；封面使用 contain，不拉伸。结果出现时尽量使用已预留的小区域，避免把正在读的评论突然推走。异步请求在原按钮/区域显示状态，不整页闪回加载占位。需要实测布局位移；用户点击后的展开也应舒适，但不能把所有视觉变化都等同于 CLS 计分事件。

5. **把交互收尾作为质感的一部分。** 详情保持“开始试玩”一个主要动作，分享/赞/讨论保持次级。当前已经有按下状态，无需新增弹跳或发光动画；应优先增大手机小图标的实际点击区域，建议从 44 CSS px 的透明命中区域试起，并保留紧凑图标。点赞、加载更多、排序等异步更新不能让键盘焦点消失；分享关闭后返回原触发按钮。评论列表目前会整段重建，需特别验证键盘点赞后的焦点。Base UI 的焦点规则为参考；具体恢复策略是 Funtrack 的实现判断。

## 排序语义与规模边界

调研时，Feed 已有“最新发布 / 最多点赞 / 最多讨论”，但 `GET /api/works` 先按创建时间取最近 200 件，再由客户端重排。这只能保证当前返回集合内的排序，不能称全站最多点赞或最多讨论。

若本轮扩展排序，应让服务端在同一个查询范围内处理搜索、作品形式、排序和分页；计数相同使用发布时间及稳定 ID 排序，防止翻页重复或遗漏。前端保留当前搜索词、筛选、排序与返回位置。只有真实存储的字段才能成为排序条件，不增加无法解释的“推荐值”。这属于本地实现建议，而非上述设计教程的直接结论。

## 克制的验收范围

- 看 0、1、4、5、12 件作品，以及筛选无结果的版面；首屏能比较多件作品，不被单件宣传区占满。
- 看长标题、缺封面、元信息换行及缩放；没有为了填满布局而复制作品。
- 看开局、退出、慢请求、失败重试及返回 Feed；位置、输入和焦点符合用户预期。
- 用键盘与 360px 手机宽度走一遍赞、评论、分享、发布；不依赖悬停，也不添加多余提示。

以上记录为实施前的只读调研。实际改动与验收边界见 `feed-and-import-validation.md`。
